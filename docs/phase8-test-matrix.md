# Phase 8A integration test matrix

Status: G8A is implemented with service PostgreSQL, API, client-state and separate browser evidence. The isolated API suite now passes 13/13. Browser round 2 passed 2/6; the subsequent sign-out HTTP repair passed its one targeted owner-switch flow. Full G8A acceptance is not claimed. This matrix derives expectations from [`phase8-contract.md`](phase8-contract.md); current results and all failures are preserved in [`phase8-verification.md`](phase8-verification.md). Optional G8B graph-checkpoint cases G01–G04 are excluded.

## Test harness and evidence boundary

The existing [`api.integration.test.ts`](../tests/api.integration.test.ts) is the closest harness: it provisions two authenticated owners, runs API migrations once, creates a fresh Core schema per test, injects a deterministic `Planner` through `createApp`, and tears down Core state and command rows. Its existing plan tests already demonstrate same-command replay, changed-message 409, Core-commit recovery after a simulated exception, and a deferred-planner lease-fencing race. These are useful primitives, not evidence for conversation history or G8 behavior.

The new suite keeps calls local and uses a real isolated PostgreSQL schema with a controllable planner. Deferred promises should hold a command in progress or make an old runner return late; synthetic `PlanResult` values should keep expected outputs deterministic. Do not use a provider, `.env` credentials, or live model calls. Assert model invocation counts through the injected planner, history through the authenticated API, database action/proof/outbox counts through the isolated schema, and unchanged server-owned message/command rows after conflicts.

Conversation identity, messages, clarification, and command links must be scoped to the test owner and conversation. Root confirmed that both API conversation and command tables can be isolated with a test `Pool` using `-c search_path=<isolatedSchema>,public`; run `migrateApi` against that pool and pass the isolated schema to Core. Use test-cookie→owner `getSession` mocking rather than concurrently running Better Auth migrations. The app exposes `app.waitForPlanning()` to await tracked background tasks. The test should not rely on UI-local storage. H02 refresh/re-login and stale UI response clearing, and the browser portion of H01/H05, need a separate browser acceptance record; this API suite cannot prove a rendered page hydrates or clears correctly.

The matrix distinguishes coverage from full criterion acceptance; a passing scenario may still cover only part of its H criterion. “API + PG” means the isolated authenticated API integration suite; “Browser” means a separate end-to-end UI check. Response codes may follow the concrete API contract, but a conflict must never silently create a new command or action.

## Execution evidence and remaining coverage

`tests/conversations-api.integration.test.ts` passed 10/10 tests against an isolated PostgreSQL schema on 2026-10-23 after extension. The first expanded run had 7 passing and 3 failing tests: both typed-transfer continuations exposed `CLARIFICATION_PROPOSAL_MISMATCH` because the deterministic planner default memo did not match the absent user memo, and the lease test assumed a per-test-empty action table. Root corrected trusted continuation memo handling while preserving the equality check; the test now verifies missing memo remains empty. The lease assertion now compares against its pre-test baseline. The rerun passed 10/10. Added coverage verifies real `createPlanner({provider:false})` duplicate-payee ambiguity and follow-up selection, one winner under concurrent CAS, source/value continuity, replay after resolution and stale-answer rejection, missing amount completion, explicit next-year goal date completion and persisted goal, post-cancel answer rejection, late-runner fencing, one final projection/action, and GET refresh of canceled Core state. That 10-case API run made no browser or live-model calls. Root subsequently added deferred duplicate acceptance/reads, new-topic isolation and pre-commit rollback; [13/13 API results](../evals/results/2026-10-23-g8-recovery-api-extended.json) passed. Separate browser results are in the phase report.

The confirmed API shape is: `GET /api/session`; `GET/POST /api/conversations`; `GET /api/conversations/:id/messages?beforeSequence=&limit=`; `POST /api/conversations/:id/messages` with `{clientMessageId,text,clarificationId?,expectedClarificationVersion?,answer?}` returning `202 {message,command,replayed}` while execution continues in the background; `GET /api/conversations/:id/commands/:commandId`; `POST /api/conversations/:id/commands/:commandId/retry`; and `POST /api/conversations/:id/clarifications/:id/cancel`. Create returns 201; retry returns 200 for completed commands and 202 otherwise. Chat-bound commands cannot be invoked through `/api/plan` (404). Create/retry response statuses and the `/api/plan` boundary were confirmed in the route implementation; the current suite asserts create/accept/retry statuses but does not directly test the `/api/plan` boundary. The fixture authenticates through a test `getSession` mock keyed by test cookies while using real isolated PostgreSQL.

The suite verifies these integration assumptions:

- The passing run exercised `search_path` isolation and `app.waitForPlanning()`; the injected planner was local and made no provider calls.
- For H06/H07 the temporary PG trigger fails final assistant-message insertion after the proposal and Core draft are committed; retry reuses that frozen proposal and keeps one draft. H07 uses a temporary PG trigger to fail assistant-message insertion; result and assistant message share one transaction, so there is no result-committed/message-missing window. H17 API uses a pre-commit DB trigger and same-ID retry; the separate browser test discards the committed response; physical connection-loss testing remains separate. The tested H15 race uses a deferred planner gate; short bounded polling is used only to observe the second command completion.
- The isolated Core schema exposes authorization-proof and Outbox counts. H15 releases the first planner only after the replacement result is durably visible, then verifies the stale result cannot add a failure message or overwrite the projection.
- Clarification assertions now cover stable clarification ID/version, typed slots and source references, successor command ID/root/parent/revision, single-winner CAS, and stale/cancelled-answer conflicts. The candidate list itself is not directly compared against the full authoritative Core payee roster.

The confirmed interfaces above are implemented. Remaining full acceptance gaps include the successful complete same-owner re-login chain, browser checks of stale action/grant expiration, concurrent ordering across separate conversations, physical database connection loss, and a comparison of the complete candidate roster. A true process SIGKILL/restart test is tracked separately from deferred promises and transaction-trigger failures. Existing `/api/plan` replay tests and standalone PostgresSaver proof of concept do not substitute for these conversation-specific criteria.

## 请求、截断与时延

[独立请求账本](../evals/results/g9-first-2026-10-24/2026-10-24T04-29-05-923Z-g9-live.attempts.jsonl)记录 **54 starts / 54 ends**，全部 HTTP 200，0 未闭合、重复或无对应记录，0 HTTP 502。43 次完成结构校验，10 次 `MODEL_OUTPUT_TRUNCATED`、1 次 `MODEL_SCHEMA_INVALID`；后者所在账单调用第二次结构成功，但最终业务仍未通过。

五条不可评业务结果都在语义阶段连续两次截断。十次截断的供应商 usage 均报告 `outputTokens=4096`、`reasoningTokens=4096`、`finishReason=length`，未形成有效 JSON。不能把这种失败称为 HTTP 服务中断；也不能凭当前日志猜测未保存的模型原文。后续应核实该端点对推理模式和输出预算参数的真实支持，再另立对照实验；本轮未调额度、未更换模型或静默降级。

供应商已报告输入 **121611**、输出 **86910 tokens**，54 次请求无 usage 缺失；这是提供方计数，未据此估算计费。全部 36 例中位数 **11.9625 秒**、P95 **48.909 秒**；11 条通过案例中位数 **15.233 秒**、P95 **26.614 秒**。大量早停澄清会拉低整体耗时，不能把较低中位数当作体验提升，也不能与不同题面的 G8N 直接作性能胜负比较。

此前 G8N 的 v2/v4/补验和浏览器日志另见 [时延观察](g9-latency-observation.md)；[独立复算](evidence/2026-10-24-g9-latency-independent-check.json)核对计数、用量和分位数一致。原有 HTTP 502 与并发窗口的时间重叠仅是相关性，不是已证实根因。

# G8M 服务端准备请求、停止准备与新浏览器恢复

日期：2026-10-24。产品方向保持“安心办 BankPilot——带资金约束的银行事务智能体”，产品架构保持总控、六领域与独立复核，资金计算、授权和执行由确定性程序控制。

## 本阶段解决的问题

G8L 保存了当前标签页的原请求，但换一个浏览器后无法发现尚未查明的准备请求；客户端也无法阻止一个尚未到达服务端的迟到请求。本阶段把请求接受和停止决定持久化到服务端，并新增“请求恢复”入口。

联系人、卡片、订阅等管理候选、理财赎回、生活目标创建与重规划共用一套准备登记。准备结果已有独立动作编号和授权流程；停止准备不会撤销已生成候选、已授权动作或已结算交易。

## 实现与复用

| 模块 | 复用方式 | 本阶段实现与边界 |
|---|---|---|
| 持久化、排他与分页 | 复用 PostgreSQL/pg 事务、行锁、唯一键和键集分页 | 新增 `preparation_requests`，不新增队列服务或数据库；分页 API 默认 20、最多 100 条，页面每页 20 条 |
| 账户与权限 | 适配复用 Better Auth 与现有 API 归属校验 | 按用户、业务类型、原编号隔离，分页游标绑定账户，所有变更继续要求正确 Origin |
| 业务结果读取 | 适配复用 G8L 的领域原单查询 | 查当前原结果，不把敏感明细冻结进登记表；订阅明细继续服从原查询授权期限 |
| 请求恢复页面 | 适配 React 与现有管理/赎回确认卡 | 仅靠当前账户的服务端记录即可列出请求，显式查询、原内容重试和停止；后续授权仍在原卡上单独进行 |
| 准备/停止协议 | 业务专用实现 | 原输入不可变、停止与创建互斥、迟到原请求受停止记录约束、并发旧状态不能复活终态 |
| 测试与故障注入 | 复用 Vitest、Playwright、现有真实本地 API/PG/Worker fixture | 独立临时 schema 和测试账户，数据库测试串行；受控浏览器与真实模型各自记录分母 |

没有新增或升级运行依赖。开源选型与许可证记录延续[开源复用与模块化决策](../research/2026-10-22/BankPilot-开源复用与模块化决策.md)，本阶段未重新声称完成全量开源活跃度调查。

## 状态协议

`PENDING` 表示服务端已保存原请求，尚未确认候选结果；`PREPARED` 表示原结果已生成；`ABANDONED` 表示此编号已停止准备。

1. API 先在短事务中保存经过校验和规范化的原输入，再进入业务准备；金额仍以最小货币单位字符串保存。
2. 候选创建事务持有同一登记行锁，检查停止状态，并将候选/目标映射与 `PREPARED` 一起提交。管理和赎回保持原用户锁顺序；停止不反向获取用户锁。
3. 停止同样锁定该记录。创建先完成则返回 `PREPARED`，引导查询原结果；停止先完成则原编号永久成为 `ABANDONED`，迟到的准备被拒绝。即使原请求尚未到达，也能先写入停止记录。
4. 重试仅使用已保存的原内容；同编号改变参数会冲突。相同 `PREPARED` 映射不会更新时间或再次推进目标。目标首次提交后，首个子动作准备失败也保留原目标；重复请求可能先读到尚未绑定子动作的目标，但不得额外推进，后续查单可读到同一个绑定。
5. 读取与响应失败不等于停止。页面在成功核实前限制重试/停止入口；迟到 `PENDING` 不能覆盖已观察到的 `PREPARED` 或 `ABANDONED`。打开生活目标时按明确目标编号选择，轮询不会覆盖用户后续选择。

旧版本的领域映射在显式重访时采用原领域 hash 校验后纳入登记；没有批量把所有历史操作加入新恢复页。服务启动前检查新表是否就绪，迁移由初始化流程或此次定向增量迁移负责。

接口包括 `/api/preparation-requests` 分页，以及单个请求的读取、`result`、`retry` 和 `abandon`。准备请求只存必要原字段及安全错误摘要，不存模型密钥、提供方异常原文或商户快照。

## 并行分工与复核

后端事务、停止竞争及物理连接故障交给 GPT-6.1-sol xhigh 子 Agent；恢复页面和状态合并交给 high 子 Agent；另一个 high 子 Agent 独立复核锁顺序、旧映射来源、只读语义和目标导航。主 Agent 负责接口衔接、故障浏览器、全仓回归、数据迁移与证据汇总。用户更换云模型后，新增 high 子 Agent 单独执行连接验证和固定样本回归，不占用数据库测试通道。

这里的能力分工是开发协作方式。产品运行时使用用户指定的云模型，各角色不因此获得自动切换服务商的能力。

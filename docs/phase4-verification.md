# BankPilot 第四阶段实现与验收记录

日期：2026-10-22（Asia/Shanghai）。阶段范围是合成理财赎回、实际到账与跨日预演、生日目标依赖计划、局部重规划，以及这些能力在既有多 Agent 工作台中的接入。接口与边界见 [phase4-contract.md](phase4-contract.md)，开源复用补充见 [phase4-reuse.md](phase4-reuse.md)。

## 交付行为

| 能力 | 已实现行为 | 明确边界 |
|---|---|---|
| 持仓与赎回 | 本人合成固定面值持仓、版本绑定、整数分金额、逐笔 Passkey、占仓与 Outbox | 零手续费合成产品，无申购、真实净值或收益推荐 |
| 到账与恢复 | 提供方双边分录、本地镜像、SETTLING 与 SUCCEEDED 分开、UNKNOWN 原单恢复 | 预计到账不能变成可用现金；已结算不能回滚 |
| 日期预演 | 当前可安排金额、日期义务、预计现金、保守现金、预计保留后余量 | 只计算不落账，不自动支付义务；仅合成周一至周五日历 |
| 目标依赖 | 赎回→等待实际到账→转账，或仅转账；每笔独立授权 | 目标日期为截止日，没有整体授权或预约自动付款 |
| 局部重规划 | 节点独立版本、保留成功赎回与回执、未变化授权保留、旧计划拒绝 | 改动待确认动作须先明确取消；已派发或 UNKNOWN 不换单 |
| 自然语言 | 理财查询、唯一产品赎回、明确日期生日目标；原工作台能进入关联确认页 | 多金额、同名收款人、不明确产品/日期安全澄清；咨询与否定不创建资金动作 |

## 并行实施与独立审查

- GPT-6 Astra（高推理）：投资账本、占仓、到账回执、成熟时间校验、worker 与真实 PG 测试；完成后独立审查 Goals。
- GPT-6.1 Sol（高推理）：持久化目标 DAG、崩溃恢复、局部重规划、模型字段约束及 Agent 测试。
- GPT-6 Luna（高推理）：理财/目标页面、移动布局、逐动作 Passkey、目标版本与动作状态合并；随后只读核对 API 对接，再修复发现的问题。
- 主 Agent：共享契约、API/WebAuthn/初始化接线、固定样本评测器、整体验证及浏览器验收。

投资账本和恢复交给高风险实现组；目标编排与模型契约交给跨模块实现组；字段明确的页面交给 UI 组，最后由主 Agent 汇总并交叉核对。这是开发分工。产品运行时的各领域和 reviewer 仍使用用户指定的 `DeepSeek-V4.1-Flash-1017-New`，没有宣称运行时已经使用三种开发模型。

复用现有 Hono、Better Auth、SimpleWebAuthn、LangGraphJS、Zod、PostgreSQL、pg-boss、React/Vite；未新增运行时依赖。没有为本阶段新造认证系统、模型编排框架或队列平台。持仓状态机、双边赎回账本、目标意图身份与到账依赖是比赛业务自研层。

## 真实模型结果与修订原因

提供方是用户配置的 `https://ai.anna.tf/v1`，模型 `DeepSeek-V4.1-Flash-1017-New`，显式 `json_object`；并发2，单例截止90秒。仅发送固定合成输入，报告无API凭据；失败保留，不切换成脚本成功。

1. 首轮8例：**6通过、2失败**。`p04`否定与`p06`理财+生日目标中，investment 将“未执行/未授权”的说明写入 clarification，导致本可继续的目标被安全拦截。原报告保留为 `2026-10-22T10-47-04-720Z-phase4-live-json_object`。
2. 修订字段契约：只有确定性解析确实缺信息时，金融领域 schema 才开放 clarification；授权提醒与边界说明放在 summary/findings。没有自动删除模型的额外字段，也没有强制reviewer通过；不合结构依然拒收。新增回归专门验证这一点。
3. 同一8例完整复测：**6通过、2失败**。原p04和p06均通过，含赎回生日目标已正确返回。剩余p01/p03在独立reviewer处出现 `MODEL_SCHEMA_INVALID`，其中p01此前还收到一次HTTP502；两者均安全停止，没有资金动作。完整报告为 `2026-10-22T10-50-31-067Z-phase4-live-json_object`。该轮中位延迟25.556秒，P95 51.615秒（仅8例）。

4. 对前3例做一次有界复测，覆盖剩余的p01/p03失败例及p02对照：**3/3通过**，原报告为 `2026-10-22T10-51-46-858Z-phase4-live-json_object`。未修改固定输入、评分规则或执行权限。该结果说明这些失败例可成功运行，不能证明上游结构输出已稳定。

不能把上述结果描述为“真实模型8/8稳定通过”。原12例与管理8例本阶段只重新运行脚本基线；其真实云端旧报告保留，不能当作本轮重跑成绩。供应商 usage 的输入token多为0，不等于没有输入或零成本。

## 浏览器验证与实际资金例子

新增流程在真实 Chromium、真实 API、真实 PostgreSQL、真实 pg-boss Worker 下运行；Passkey 使用浏览器虚拟验证器产生签名，由真实服务端验证，不伪造成功响应。T+0/T+2均走相同提供方与回执路径，没有修改成熟时间或直接加现金的后门。

已完成的独立流程包括：

- T+2赎回100.50元强验证后进入SETTLING，现金仍8000元；时间线单列预计100.50元。
- 创建500.25元生日目标，资金来源为T+0赎回1000元，检查请求金额确为50025分。
- 赎回实际到账后现金9000元；未准备/未授权转账时不付款。
- 将后续目标改为600.75元，计划版本升至2，已成功赎回的动作ID及provider回执不变。
- 单独确认600.75元转账后，目标完成、现金8399.25元；T+2仍未到账。
- 刷新恢复目标与回执，390px移动屏无横向溢出。

初次新增浏览器检查在收款人下拉定位处失败，已补清晰的可访问名称后通过。测试从随机新用户重新开始，不重置演示账户余额。最终全量浏览器运行：**4/5通过**。账单、管理、新增赎回目标闭环与真实云端生日提案均通过；原转账的第二次云端请求出现 `transfer MODEL_SCHEMA_INVALID`，被安全拦截，因而未完成该条浏览器验收。报告保存为 `evals/results/2026-10-22-phase4-browser.json`，失败 trace 单独保留。该问题与真实模型固定样本中的结构稳定性限制一致，不能把全量运行说成全绿。随后对该转账流程单独复测：**1/1通过（45.3秒）**，黄档→红档Passkey→记账后UNKNOWN→原单查单→两次扣款账本一致全部验证；报告为 `evals/results/2026-10-22-phase4-transfer-retest.json`。因此5条流程均有本轮成功证据，但不是同一轮5/5无失败。

## 当前限制与后续阶段

G4是比赛合成环境的实现与技术验证，不代表真实银行适配、生产认证或赛事平台验收。只支持显式YYYY-MM-DD目标日期；T+N日历不包含法定节假日。投资到账保留在独立投资时间线与回执，未汇入历史账单分类分析；不实现申购、行情净值、真实商户扣款调度或自动预约支付。完整聊天历史与主业务LangGraph检查点仍未整合，已有PostgresSaver恢复为独立PoC；主业务依赖API提案快照、Core动作及Goal节点意图恢复。

下一阶段是G5公平评测与比赛演示收敛：固定独立保留集，在相同模型、工具、账户、授权与预算下比较单Agent、六领域并行、独立复核的增量；继续单列完成率、结构失败、拒绝质量、资金错误、重复扣款、恢复、延迟和供应商用量。优先解决云端reviewer结构稳定性，再宣称更广的模型可用性。

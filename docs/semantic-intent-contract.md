# Grounded semantic intent contract

G7 adds a semantic interpretation stage before deterministic domain planning. The model identifies the requested operation and points to verbatim source text. Server code resolves identifiers, parses money and dates, and produces canonical messages and typed slots. This component has no execution, authorization, balance-update or scheduling capability.

## API and integration

`interpretSemanticIntent(input, { provider, referenceDate?, adapter?, observer? })` returns `SemanticIntentResolution`. `validateSemanticIntent(input, raw, { referenceDate? })` performs the same deterministic grounding without a provider call. `semanticIntentSchema` is the strict Zod schema with grounding constraints; `invokeStructured` uses the same wire shape with the bounded source-copy refinement described below.

A resolution contains `status` (`ready`, `clarification`, `no_action`), `tasks`, optional `clarification`, `findings`, `modelRuns`, and `recognizedRoles`, plus optional safe `issues` diagnostics. Each issue has `path: string[]` (for example `["tasks", "0", "entity", "mention"]`), `category` (`schema`, `source`, `ambiguity`, `entity`, `value`, `safety`) and a stable `code`. Paths are built only from known schema fields and array indexes. Neither diagnostics nor clarification echo model completions, entity IDs or submitted span text. Existing `findings` codes remain available for consumers. Recognized roles describe schema-valid semantic classifications, including interpretations subsequently rejected by grounding. They are not evidence of an executed domain agent. Schema-invalid/provider-failed responses cannot supply recognized roles.

Each validated task contains `operation`, `role`, original `source` span, `canonicalMessage`, and `slots`. Slots may contain grounded `entityId`, integer `amountMinor`, exact `memo`, `targetDate`, goal funding `{ positionId, amountMinor }`, or `billPeriod`. The model schema has no `amountMinor`, normalized date, balance, version, authorization or execution fields.

Operations are `transfer`, `funds_query`, `bills_query`, `investment_query`, `investment_redeem`, `card_query`, `card_report_lost`, `card_restore`, `subscription_query`, `subscription_cancel`, `subscription_block`, `goal_create`, and `unsupported`. `funds_query` maps to the existing goal-domain funds preview, never future-goal creation. A catalog product containing “计划” is an investment entity, not a goal trigger.

The orchestrator should interpret once, retrieve server context for the validated tasks, and reuse the prepared interpretation for planning. Keep original user text available to supervision/review; never replace its provenance with only the canonical message. Select branches from explicit task roles/operations. In particular, distinguish `funds_query` from `goal_create` by operation, not a regex over canonical text.

Canonical messages are compatible with existing strict domain resolvers: transfer names include a grounded account suffix; investment redemption uses an authoritative position ID separated from the explicit amount by whitespace and the 金额 label, preserving the numeric parser boundary; goal funding includes a separate redemption clause; card operations retain grounded name/suffix. Domain resolvers still own position availability, versions, grant expiry, target-account matching and draft rules. Apply the validated transfer `slots.memo` to the pending proposal explicitly: the legacy transfer resolver's default memo is not a source of user intent. Treat memo content as data and preserve it verbatim.

Bill periods are metadata for fetching the correct report, not a request to relabel an existing report. `billPeriod` has `kind: month | range | selection`, `startPeriod`, `endPeriod`, and its raw source span. A selection additionally contains exact `periods`; its bounds never imply intervening months. Explicit full-year months, shared-year month selections and ranges are parsed deterministically. Relative months require a trusted `referenceDate`; month-only text without a year requires clarification. The API must not silently pick the current year. Ranges are limited to 12 months. Actual reports carry complete/partial/missing coverage; missing months are not zero-spend months, and comparisons need complete coverage. Deterministic bill analysis uses server transactions and integer amounts, with unsupported questions explicitly clarified.

## Grounding and fail-closed rules

For exactly one task, `scope` may be the strict explicit reference `{ "source": "whole_message" }`. The server then obtains the exact original slice `input.message.slice(0, input.message.length)` and its UTF-16 bounds. This avoids asking a model to copy Chinese punctuation; it does not normalize punctuation or any other character. No missing scope is filled automatically, and legacy text spans are never expanded or converted into this reference. Multiple tasks containing this marker still fail deterministic schema validation. G8D adds only the separately bounded two-task regeneration described below; it cannot remove a task. Whole-message references still undergo every source, quotation, negation, entity, money, date and operation check. An additional detected domain or repeated transfer operation is rejected; an explicit trailing memo remains data for this additional-operation check. Goal funding remains part of its goal task.

Legacy copied scopes retain one narrowly bounded source-copy regeneration through the existing provider attempt/deadline/output budget. Only eligible single transfer/funds-query drafts with a missing scope and independently checked remaining fields can request it. The second draft may correct the scope or explicitly select `whole_message`, but must retain all non-scope semantic fields and verbatim slot texts; optional offset representation may change. Drift returns `SEMANTIC_SOURCE_REPAIR_DRIFT` with the changed field path and no tasks. Exhausted copy failures preserve their source diagnostics. Failed raw output is never supplied as repair feedback, and scripted adapters remain single-pass.

A separate bounded repair can request a missing or unparsable bill period only for one read-only bill task whose scope already covers the whole original message and whose complete period is uniquely determined from that message. The initial failure must be PERIOD_REQUIRED or PERIOD_NEEDS_EXPLICIT_YEAR_OR_REFERENCE; nonexistent source spans do not qualify. It shares the existing two-attempt/output budget, does not silently insert a period, and binds operation, disposition, task count, scope and all other fields. A cropped scope cannot enter this repair; adapters remain single-pass. When a valid full period already exists in source, a remaining failure asks the user to retry because the system could not verify that supplied period, rather than falsely asking for a missing year.

G8D's multi-task source repair requires exactly two existing tasks, bills_query followed by transfer, at least one whole_message reference, exactly one unambiguous clause separator, and independently valid original bill period/payee/amount. It excludes memo, funding, separate dates, quoted/negative/conditional/historical source and candidates requiring a simultaneous field repair. Server code constructs a temporary candidate only to prove eligibility and bind expected grounded tasks; it never returns that candidate as an accepted model interpretation. The provider must regenerate exact scopes while preserving task count/order and all other field texts. The complete second validation must equal the prevalidated grounded tasks, otherwise SOURCE_REPAIR_DRIFT stops planning. Three tasks and same-domain multiple tasks remain outside this repair.

A distinct read-only classification repair applies only to an entire explicit dated monthly income/expense/net summary incorrectly classified as funds_query. It can bind bills_query and the unique original period, with all other fields absent and scope unchanged. Current funds, protected balance, future budgets, mixed requests and any conditions remain ineligible. The bound repair cannot switch strategies or borrow a later attempt budget; it uses the existing provider maximum of two attempts. Prompt guidance also distinguishes bill totals from current available funds.

Before returning `ready` or `no_action`, the validator checks coverage of the entire original message using only individually grounded and validated scopes. Uncovered meaningful source text returns `SEMANTIC_SOURCE_COVERAGE_INCOMPLETE`, including when a model already supplied a correct period but omitted a later task. Negated and historical dispositions require source evidence for each independent clause; a model label alone cannot cover a current request. Punctuation, explicit conjunction/request prefixes, and a narrowly parsed record appendix containing one complete amount may be outside scopes. Appendices containing an entity, date, command, negation, multiple amounts or trailing business text are rejected. This check does not enlarge scopes or invent omitted tasks.

Model spans require verbatim `text`. UTF-16 `start` and `end` offsets are optional. Scope text is located in the whole message; each slot is then located within that validated scope. Unique text is located by server code; repeated text within the relevant scope requires valid offsets. `SEMANTIC_SPAN_NOT_FOUND`, `SEMANTIC_SPAN_NOT_UNIQUE` and `SEMANTIC_SPAN_OUTSIDE_SCOPE` distinguish nonexistent, repeated and out-of-scope text and identify the failing field. The server does not enlarge a cropped scope to recover an omitted antecedent. A task such as a named card followed by a restoration request must include both clauses in its model-provided scope. Every entity/amount/date/period/memo must occur within its declared request scope. Numeric token boundaries reject cropped digits, decimals, signs, exponent fragments and partial dates/months; exact grounded digit-ending entity names can adjoin a complete amount. Entity argument boundaries reject longer unknown names, conflicting name/suffix pairs and ambiguous relational recipients. A request scope must cover a punctuation-delimited clause or the whole request, preventing the model from cropping away a preceding negation. Entity edges distinguish human-name arguments from typed four-digit tail locators and nonhuman object state/container predicates. Card state descriptions such as a card having been found can supply the subject for an explicit subsequent restoration request; a completed banking operation remains historical. Tail digits cannot be cropped from longer numbers. Exact names embedded in longer unknown names or relational recipients still fail closed.

Catalog IDs must match exactly one grounded mention in the permitted server catalog. Position aliases remove only an authoritative trailing T+n settlement suffix. Duplicate aliases cannot be resolved by the model choosing an ID. Two different mentioned recipients cannot silently become a transfer to the first. Missing, unknown or ambiguous entities yield clarification and no task.

G8C v2 permits the noun 赎回产品 only within trusted built-in position names verified against the shared immutable product ID, full name, settlement days and calendar. The command scanner uses a local noun substitution; original message/spans stay unchanged. Redemption still requires a separate explicit operation outside the noun and one complete source amount. Name plus amount alone, additional same-domain operations, altered metadata and non-position catalog aliases do not acquire permission from this noun exception.

Card-tail locators must include an explicit 尾号 or 末四位 label; bare four-digit fragments are not identifiers. G8D's pure inspectCardLocator verifies the entire original scope and optional 卡/银行卡/卡片 container or exact saved card name. Tail and name must select the same unique catalog item; unknown prefixes, five-digit crops, duplicate tails, conflicting names and multiple different locators cannot be resolved by model-selected IDs. Original mention remains unchanged and existing negation/right-boundary checks still apply. Read-only card collection queries can remain one task without guessing a single card. The anchored subscription-block form “保留…会员，但银行侧阻止…” is scoped to that operation and does not broaden transfer beneficiary matching. “可赎回余额” is an investment query, not a separate funds-query task. A trailing standalone 不转账 constraint may coexist with a read-only task; when further meaningful text follows that exclusion, validation remains conservative so later colloquial payments are not suppressed.

Money is parsed from a complete explicit-currency token with the existing integer parser. Common full-token “三百零七块五/块五毛” forms are deterministically converted to yuan/jiao before that parser, yielding 30750 integer fen. Invented numeric fields, partial malformed tokens, extra explicit amounts and conflicting options are rejected. No floating-point money calculation is used. Dates must be complete, real calendar dates from source text. A goal's funding amount must belong to the funding entity's redemption clause, distinct from the target amount clause, preventing swapped monetary roles. Explicit goal text cannot be classified as an immediate transfer/redemption even when no goal task is emitted. A goal's funding redemption remains a dependency of the goal; a simultaneous immediate transfer/redemption task is rejected.

Quoted, historical, hypothetical, negative and retracted instructions are data. Quotation around an exact catalog noun may identify the request object; it does not make the entire request historical. A quoted unknown product noun requires product clarification, including when the model incorrectly marks that current request as quoted. The quoted-noun exception removes the quote punctuation before checking surrounding entity argument boundaries, so quoting a known name cannot hide an unknown name prefix or a different relational recipient. A complete quoted instruction remains nonactionable. A model `quoted` disposition without typographic quotation is accepted as nonactionable only when the complete message has an explicit example, text-processing or historical-record wrapper; an ordinary current request mislabeled `quoted` still requires clarification. An explicit outer text-editing, translation or recording request also vetoes a model-proposed mutation, even when only the entity noun is quoted. Unknown noun quotes deliberately do not guess an alias. Model disposition is checked, and deterministic guards veto unsafe request classifications. Subscription routing and grounding reuse the shared historical-bill clause filter. Existing deterministic subscription resolution additionally vetoes bank-block/merchant-cancellation contradictions. These safety checks grant no action permission. An empty interpretation, unsupported request, invalid schema, provider failure or grounding conflict produces explicit clarification; there is no silent scripted fallback after model failure.

## Reuse decision and evidence

Direct reuse: existing `invokeStructured`, Zod, server catalogs, integer money parsing and the strict domain resolvers. Existing provider support already offers a constrained tool-call or JSON-object transport, runtime Zod validation, model-attempt diagnostics and bounded retries. No new dependency is needed for this layer.

LangChain's official JavaScript documentation distinguishes provider-native schema output from function/tool-based structured output. Both enforce structure; neither establishes factual grounding or financial authority. The server-side grounding layer is therefore required even when provider-native schema support exists. Relevant primary references:

- [LangChain JavaScript structured output](https://docs.langchain.com/oss/javascript/langchain/structured-output)
- [providerStrategy API](https://reference.langchain.com/javascript/langchain/index/providerStrategy)
- [toolStrategy API](https://reference.langchain.com/javascript/langchain/index/toolStrategy)

A new LangChain agent wrapper would duplicate the existing transport/validation layer and introduce dependency/API surface without removing the need for these deterministic checks. Reconsider native provider strategy only after provider capability and compatibility evidence is available.

## Validation modes and limits

A complete single-clause request explicitly ending with “只是个示例” or a supported equivalent can ground a quoted/negative/historical disposition as no_action. A later actual request cannot be swallowed by that label. Mixed content requires independently complete scopes or clarification; coverage of all original text remains mandatory. A model that labels an ordinary live request as inactive still needs corresponding source evidence.

An injected semantic adapter runs deterministic grounding tests with supplied classifications; it performs no live inference and returns no fabricated provider-attempt records. Legacy scripted regression tests exercise existing deterministic routes/resolvers and do not demonstrate semantic language coverage. A cloud semantic run includes the semantic model call plus downstream domain/review calls, each recorded separately. Unit tests with mocked fetch verify transport/schema behavior, not live model quality.

Missing or ambiguous transfer beneficiaries explicitly ask for a 收款人; missing investment, card and subscription identities ask for the corresponding object. These questions do not create conversation state or resolve unavailable prior turns. Synthetic quality regressions cover these contracts independently of the frozen evaluation fixtures. Passing them shows deterministic validation behavior, not that the live model will supply the correct scope or all required spans.

Current safeguards intentionally prefer clarification for unsupported date forms, ambiguous repeated spans, multi-task same-domain requests and uncertain scope boundaries. These are explicit quality limits, not evidence of end-to-end transaction acceptance. Semantic correctness, deterministic grounding, model JSON completion, pending-draft creation, confirmation and actual execution remain separate validation layers.

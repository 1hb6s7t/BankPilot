# G9E 原文修复与首轮覆盖契约

本阶段针对 G9D 已保存的真实抽取：重复别名两轮都缺坐标、持仓集合被绑定到单一产品、独立任务遗漏及 mixed whole/literal scope。原 G9D 冻结副本、manifest、原 48 题、标签、评分器和报告保持不变。本阶段不以改分或扩大来源校验容忍度修复结果。

实现位于 [`semantic-intent.ts`](../packages/agents/src/semantic-intent.ts) 的 source 修复、查询范围门禁与提示段；历史/引用识别 helper 由独立任务负责。来源、覆盖、实体唯一性、金额、否定及同领域多任务限制继续适用；原先仅针对内置产品名的查询 scope 正则由统一完整查询范围门禁代替。

## 唯一 source 几何位置绑定

原 G9D 的重复别名只允许模型重新提交 offsets，真实 `transfer-03` 两轮返回了相同的无坐标原串。G9E 增加一种严格受限的服务端 source 坐标绑定，不能理解为新增或改选实体：

1. 第一轮必须是直接 `entity.mention` 的重复文本问题，原 kind/id、mention 文本、操作及所有值保持原样。
2. 第一轮与第二轮都必须**完全省略 start/end**。任一轮有显式或 partial 坐标，都不使用新 binder 覆盖；首次错误坐标只能由模型第二轮提交真实正确坐标并通过全校验。
3. 在最多 32 个原文 occurrence 中，必须恰好一个位置独立通过完整原文、实体、否定、金额、操作及覆盖校验，而且不存在未检查的剩余 occurrence。两个合法位置不默认选择 `legal[0]`；超过上限不能宣称唯一。
4. 仅在已经进入一次受限重提取、第二轮仍缺坐标时，才将该唯一几何位置绑定到第二轮草稿副本。不会直接返回候选任务、改写原 mention、补金额或选择另一个 ID；绑定后仍完整验证，并与已证明的非 source 结果一致。
5. 真正使用服务端绑定的成功结果包含 `SEMANTIC_SOURCE_OCCURRENCE_BOUND` 诊断，区分模型主动给出位置和服务端几何定位。输入对象、原模型输出及 raw 观察保持原样，不能宣称第二轮模型补齐了它实际上没有输出的坐标。

上述“显式错坐标不覆盖”专指**新增 binder**。既有 `locate` 在唯一文字情形下的 fallback 没有在本阶段全面重写，不能把新 binder 的严格性宣称为所有旧 span 入口的统一行为。单 attempt、禁用结构 repair、纯 adapter 或直接 `validateSemanticIntent` 不会自动获得此绑定。

## Mixed scope 与无筛选集合的不同修复

mixed whole/literal scope 的新增资格仅适用于全部为只读 query 的多任务。仍需在原有最多 4 个 task、10 个引号外标点、48 个分区中证明完整合法范围；任务数量、顺序、操作、disposition、期间及其他槽位均锁定。含写操作的 mixed 编码保留此前的单次拒绝边界。重提取后每个 scope 仍须由模型提交并独立通过完整校验。

无筛选持仓集合另设一个明确的新契约，不能与通常的 source 修复混为一谈：

- 仅允许 `investment_query`，没有金额、日期、purpose、memo、period 或 funding 等不应出现的槽位。模型给出的 position ID 必须存在，mention 必须是完整的无身份集合泛称，例如 `我的理财持仓`。
- 该泛称不能是任何目录名称、别名或 locator；不能借“看起来像集合”的名称抹掉真实产品身份。命名产品、T+N、金额/余额范围、部分对象、多对象筛选、引用、否定查询及条件表达均不符合本契约。
- 原文整个集合 scope 必须由有限的完整正向集合查询、明确不赎回限制、字段展示或完整预览要求解释，且只包含一个正向集合查询。
- 其他 task 的每个非 slot 子句同样必须有**完整正向语法证明**，当前覆盖确定的转账、卡状态查询、账单收支汇总及完整 goal_create（含已验证 funding）结构；合法对象、金额、期间、用途、日期、funding 和完整 memo 先按已验证原文绑定成类型标记。完整动作、声明对象/金额、明确现金来源、完整备注、目标截止与筹资依赖/分别授权关系或展示约束可以解释原文，未知残余则无资格。不能把 `收益率超过3%`、`按到期时间排序`、`返回首条`、`只保留正常状态` 等修饰片段移入另一个 task 后，假称集合没有筛选。
- 这项资格只允许**模型在第二轮删除那个已证明无原文身份根据的 singular entity**，服务端不会自动删除。第二轮不得保留或更换该 entity，也不能修改 task 数量、顺序、query 操作、disposition、其他实体及转账金额/备注/来源；最终仍完整验证并锁定已证明的非 source 结果。

这不是通用实体纠错或通用查询补全。有限资格语法不取代正式提取与完整验证；首轮与第二轮的 investment_query 均还要满足下述独立范围门禁，未被正向语法证明的组合保持澄清。

## 独立任务遗漏仅改善首轮提示

模型输入新增 `sourceInventory`：最多 24 个完整原文单元，使用 UTF-16 start/end/text，只按引号外标点分段，不切引号中的标点或 `1,418` 一类数值逗号。若超过上限则不提供片段列表，仍保留完整原消息。单元没有领域、操作、金额解释或候选答案。

固定提示要求输出前逐单元核对所有当前独立请求、集合查询和局部否定。它只帮助模型首轮覆盖，不能保证模型一定不漏任务。若原抽取只有 card_query 而整个 bills_query 与 period 都缺失，source 修复仍不能自动增加任务或补造操作。该问题必须在真实模型评测中独立验收，不将提示变化当成已解决。

## 首轮查询范围缺口的发现与共同修复

本阶段先以纯本地输入确认了一个与 repair 资格不同的基础查询问题：若**首轮已经省略 entity**，原 base validator 对下列消息返回 `ready`，canonicalMessage 均为无筛选的 `查询理财持仓`、slots 为空：

- `查询我的理财持仓，只看收益率超过3%的`
- `查询我的理财持仓，按到期时间排序`
- `查询我的理财持仓，返回首条`
- `查询我的理财持仓，只查最近到期的`

相比之下，`只看余额超过500元的` 被既有 `SEMANTIC_WHOLE_MESSAGE_EXTRA_OPERATION` 拒绝。修复没有增加收益、到期、状态筛选、排序或行数计算，而是增加独立正向范围门禁：

- 每个正式 investment_query 的完整 scope 必须由无筛选集合查询，或明确单一已 grounded 对象的基本事实查询解释。允许持仓、名称、本金、预留/占仓、可赎回余额及到账规则等事实字段、完整展示要求、明确只查询及局部不赎回/不转账。对象文字只在已经通过原文唯一定位后替换为内部类型标记；服务端不从这套语法选择实体。
- 每个子句都要完整匹配；未知残余、收益/到期条件、排序、首条、部分对象或多对象过滤均澄清，不能通过删除条件输出全部持仓。`SEMANTIC_INVESTMENT_QUERY_SCOPE_UNSUPPORTED` 标识新门禁，既有来源、否定及额外操作错误可以先于它拒绝请求。新门禁失败本身不启动 source repair。
- 包含 investment_query 的多任务还要证明其他 scope 的非 slot 子句，避免模型将查询条件移到另一 task 后丢弃。这项共同门禁在既有覆盖、重叠、同领域多任务检查之后执行，保持已有错误优先级。允许的 companion 为上述完整 transfer、card_query、bills_query 与 goal_create 结构，以及已经独立证明的 inactive scope；其余未建立完整语法的组合保守澄清，不宣称本轮支持所有跨领域语言。
- query A + funded goal B、同一产品的 query + funded goal、集合 query + funded goal 均保留各自准确 source 和已验证槽位；goal 的日期、目标金额、用途、筹资对象/金额及依赖关系不能被这套门禁改写。financial/index 中实际单对象过滤及两种读范围合并由独立实现/测试负责。
- 仅当完整合法 slot 已验证，备注里的 `按到期时间排序，返回首条` 才作为原样数据保留，不能因包含筛选词而误删。未知指令残余仍不被当作备注。
- 新查询门禁的礼貌/顺序前缀采用最多 8 token 的确定性扫描，避免 `我想先` 与 `我想` + `先` 在长不可信文本上产生正则指数回溯。

这是不支持范围的明确澄清契约，不是新筛选能力。原分数、原标签及冻结文件不因此修改；新的真实模型效果仍待冻结后验收。

## 预算、验证与证据边界

仍沿用同一 `invokeStructured`：固定 2 attempts、1 structural repair、每次 semantic 4096 输出上限、60 秒请求超时、180 秒共享 case 截止和 32768 总输出预算。网络/JSON/schema/source 修复共用原额度，不另起调用、不增加第三次重试。基础 schema 或 HTTP 故障仍保留为系统结果，不借来源错误伪装成业务澄清。

[`g9e-semantic-source.test.ts`](../tests/g9e-semantic-source.test.ts) 包含 108 项受控测试及反例：两轮省略坐标、两轮显式/partial/正确坐标配对、多合法位置、32 上限、语义字段漂移、mixed 只读、写操作、无身份集合、命名产品/locator/类似泛称目录名、首轮/repair 的金额/收益/时间/状态/部分对象筛选、跨 scope 修饰移位、合法 memo、首轮遗漏任务、原文单元完整性及 query A + funded goal B。中间检查曾为 50 项 49 过，筛选移位反例发现资格漏洞后才改为其他 scope 的正向完整语法；没有修改反例期望。

最终定向回归为 21 文件、950/950 通过（含新 source 108 项、inactive helper 及独立 investment 查询范围集成测试），`pnpm typecheck` 通过。共同门禁初次回归曾因缺少既有合法 `同时` 转账 wrapper 出现 949/950，补齐该完整 wrapper 后通过；原测试与期望未改。

这些是纯本地受控验证，没有本子任务的云模型或数据库调用。新诊断与新资格契约必须通过后续冻结候选真实 raw trace 单独核验；不能据本地测试宣布原 48 题真实改善，或把明确拒绝未支持筛选声称为已经实现这些筛选。独立任务遗漏仍只有提示改进，不能据此宣称完全解决。

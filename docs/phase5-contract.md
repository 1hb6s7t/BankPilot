# G5：冻结样本、编排对照与可诊断性

本阶段评估同一银行规划系统中，单次联合模型调用、按领域并行、并行后独立复核的差别。生产继续使用“按需领域并行 + 独立复核”，评测开关不暴露到 HTTP API 或用户界面。

## 复用与开发分工

沿用已调研并固定版本的 LangGraphJS 编排、Zod 结构约束、Node 原生 HTTP/crypto、Vitest 和 Playwright。没有引入另一套评测框架或模型评委；领域解析、上下文裁剪、严格动作 schema、资金门禁与既有执行底座共用。新增部分是实验拓扑、手工标签、银行动作断言、冻结清单和脱敏诊断。

开发协作按用户既定要求并行：GPT-6.1 Sol 负责编排改造与定向测试；GPT-6 Astra 负责 provider 诊断、评分与安全边界的独立审查；GPT-6 Luna 负责手工样本、演示与问题分类。主线程负责冻结检查、统一评分器、真实模型运行、整合与验收。这是开发分工，与产品内部的 Agent 角色分开。

## 三种模式

| 模式 | 模型工作 | 保留的共同约束 |
|---|---|---|
| single | 一次接收全部活跃领域最小上下文，按严格 tuple 返回全部领域提案 | exact schema、每领域语义校验、角色完整性、确定性资金与澄清门禁 |
| parallel | 同样的领域上下文分别并行调用，没有模型 reviewer | 同上 |
| parallel-review | 同样的领域并行，再由独立模型 reviewer 检查结构化事实 | 同上，并保留 reviewer 可拒绝提案的判断 |

所有条件都没有银行执行、强验证或授权工具。模型不能改变确定性余额与动作参数。API 后续是否准备待确认动作、Core 是否授权、实际是否记账，是独立链路。

当前模型接收的是共同的确定性解析结果，而非直接自主解析完整原始银行任务。领域输出的可信金额、证据与事实由服务端保留，模型叙述另列为解释证据。因此实验主要检验编排、结构输出与复核可靠性；不能据此证明语言理解、复杂规划或端到端金融自治能力更优。

## 样本冻结与首次使用

`evals/holdout-fixtures.ts` 包含 40 条新合成场景；`evals/holdout-manifest.json` 记录版本、SHA256、首次运行前人工数据预检修订，以及预先选好的 12 条云端样本。它们覆盖六个领域、金额、歧义、否定、资金保护、数据注入与目标赎回依赖。

标签由独立 Agent 依据阶段契约手工编写，未通过 planner 或 resolver 生成。首次运行前纠正了 NaN 尾号、不存在的交易引用及未来目标与即时支付的标签混淆；这些数据修正写入清单。首次运行后不改标签、不删除失败、不按分数选择云端样本。使用后的集合转为回归集，后续需要新的未见集合才能重新称为泛化验收。

目标的自由生成标题只检查合法性，不要求与未由用户指定的标题逐字相同；账户、收款人、整数分金额、日期、持仓、版本和授权查询引用仍精确比较。必要事实可出现在摘要、澄清、发现或证据中，不强迫出现在同一个文案字段。

## 预算、顺序和可复现性

- 同一 `.env` 指定的云端提供方、模型与输出模式；显式 temperature=0。
- 三种条件各有同样的 120 秒用例截止和 12288 输出 token 请求上界，传输错误最多两次尝试。每次 `max_tokens=floor(12288/(逻辑调用数×2))`，包括可能重试；结构失败不自动重试。
- 逻辑调用数来自实际领域路由，不读标签：single 为1，parallel 为N，parallel-review 为N+1。无领域时不发模型请求，不能冒充模型成功。
- 用例间串行，每三例轮换三种条件的先后位置；领域并行仍是真并行。所有条件使用深克隆的相同输入和相同标签指纹。
- 起止实现哈希、fixture/评分器/runner 哈希都进入报告；中途源码漂移则比较无效。逐例 JSONL 先落盘，最终生成 JSON/Markdown。

这里控制的是输入、模型、规则和预算上界。调用数量、提示 token、实际消耗不相等，温度0也不能保证供应商确定性。供应商的输入 usage=0 单独记录，不能解释成无输入或免费；不估算费用。

## 评分与测量范围

综合通过要求角色、动作、金额、澄清、资金拒绝、账单证据、模型最终返回以及复核拓扑都满足断言。HTTP 502 后重试成功可以算“模型最终完成”，但首次无失败、失败尝试、结构错误会另计。没有有效模型结果的安全关闭不能算完成任务。

缺少本应产生的动作属于质量失败；产生错误或重复的动作、否定后仍提案、隐私名称泄露属于规划安全失败。这里的“动作”指提案，不能直接等同于发生扣款。没有连接数据库和执行工具的矩阵把实际越权写入、错账、重复扣款与恢复指标记为未测，而不是0。执行边界另用真实 PostgreSQL、API、Worker、签名和浏览器验证。

一次12例试跑只提供描述性证据，不做统计显著性、稳定性或“多Agent更优”的断言。原始失败保留，修复后运行必须标为已见样本回归，与首次结果分开。

## Provider 诊断

`ModelRun` 记录尝试编号、请求/响应JSON/工具输出/输出JSON/schema阶段、最多8项安全字段路径、白名单错误代码/类型、结束原因、输出长度和SHA256。未知字段名、record动态键、模型值、请求头、API Key与响应原文不进入诊断。

G4历史 `MODEL_SCHEMA_INVALID` 只有泛化错误码，无法倒推出具体坏字段。G5对旧p01做过一次隔离reviewer真实调用，成功且没有复现；这不等同于修好历史问题。新诊断服务于后续实际失败定位，仍严格拒收非法结构，不删字段、不强制approved、不回退脚本成功。

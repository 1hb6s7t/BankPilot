# 第二阶段：账单、资金保护与真实模型契约

日期：2026-10-22。延续第一阶段的身份、授权、动作哈希与未知结果恢复约束。所有金额仍为整数分字符串；数据来自本地合成银行。

## 数据与职责

| 模块 | 权威数据 | 职责与边界 |
|---|---|---|
| FinanceService | PostgreSQL 历史流水、成功动作、资金策略 | 计算账单合计、分类、规则提示及可用资金；不调用模型 |
| 领域 Agent | 服务端裁剪后的账单、资金事实、收款人候选 | 生成结构化提案；只按任务激活相关领域 |
| 独立复核 Agent | 领域提案、确定性检查结果 | 核对提案；不能覆盖服务端金额、资金拒绝或执行权限 |
| API | 当前会话、计划命令、提案快照 | 生成任务 ID，校验数据归属，冻结提案后创建待授权动作 |
| 执行核心 | 动作、策略、在途占额、用户锁 | 授权和派发前重算保护边界；模型没有直接执行入口 |
| UI | API 返回的事实与状态 | 展示原交易、预算缺口、确认入口、模型调用结果和最近计划 |

运行时领域及复核共用用户指定的云端模型。开发过程使用不同能力模型的并行分工，是独立的开发协作方式。

## API

所有下列接口均要求 Better Auth 会话。写接口继续校验可信 Origin，调用方不能在请求体中指定用户身份。

| 接口 | 输入 | 返回 / 行为 |
|---|---|---|
| `GET /api/bills` | 可选 `period=YYYY-MM` | `BillReport`；默认上海业务日当前月 |
| `GET /api/funds` | 可选 `accountId`、`amountMinor`，默认金额 0 | `FundsOverview`；只读预演，不占额 |
| `POST /api/funds/policy` | `expectedVersion`、`minimumBalanceMinor`、`obligations`、`confirmed:true` | 返回新版策略；同用户锁内更新并记审计 |
| `POST /api/plan` | 第一阶段的 `commandId`、`message` | 可追加 `billReport`、`fundsPreview`、`modelRuns`；金额或收款人歧义要求澄清 |
| `GET /api/dashboard` | 无 | 追加 `latestPlan`；动作状态从当前数据库重新读取 |

账单查询支持“本月”“上月”及明确 `YYYY年M月`、`YYYY-MM`、`YYYY/M`。未指定月份时默认为当前月；尚未支持任意自然语言日期区间和跨月聚合。

资金策略中的每个义务包含 `id`、`title`、正整数分 `amountMinor` 和真实日历日期 `dueDate`。上限 100 项；ID 不得重复，未知字段拒绝。并发版本冲突返回 `POLICY_VERSION_CONFLICT`，前端重新加载供用户核对。

## 账单证据

`transactions` 是所选月份流水；`evidenceTransactions` 包含周期提示引用的前一期流水。分类只汇总支出，各类别合计必须等于支出总额。历史收入是账单事实，不会再次写入当前余额。

- `LARGE_EXPENSE`：单笔支出达到 1000 元的金额规则提示。
- `POSSIBLE_DUPLICATE`：同账户、同日、同商户、同金额的多笔支出，不能直接断言重复扣款。
- `RECURRING`：前一期有同商户同金额的合成账单支出，不能直接断言已订阅。

每条提示必须带可定位的交易 ID。成功沙箱转账从唯一已结算动作派生，重复查询不会重复计入。尚未实现用户账单上传、自动纠错或模型分类入库。

## 资金预演与执行

```text
保护金额 = 最低生活保留 + 未来 30 天及逾期未清义务合计
支出前可用 = 当前余额 - 有效已授权 / 已派发 / 结果未知占额
支出后可用 = 支出前可用 - 本次金额
可自由安排 = max(0, 支出前可用 - 保护金额)
缺口 = max(0, 保护金额 - 支出后可用)
允许 = 缺口为 0
```

未来收入不计入可用资金。所有义务条目代表尚未清偿的支出；本阶段由用户确认编辑维护，不会自动把任意转账匹配为房租已付。

预演不是授权。授权时在同一用户锁内重新计算，突破保护边界返回 `FUNDS_PROTECTED`；派发前再次检查并排除该动作自己的占额。若策略变更导致未派发动作不再满足条件，将动作记为失败并释放占额和当日额度。已经 `SUBMITTING` / `UNKNOWN` 的动作继续原单查单，不能因策略变更释放占额或重复派发。

## 模型适配与失败

根地址自动规范为 `/v1`，通过兼容的 `chat/completions` 接口请求结构化工具输出；也支持明确配置的 `json_object` 模式。两种模式使用同一 Zod 契约，不会静默互相降级。

仅读取项目专属 `BANKPILOT_MODEL_*` 配置；密钥不进入浏览器、版本库、模型评测报告。超时、网络错误和 408/429/5xx 可有限重试；永久认证错误、输出结构错误不自动重试。每次尝试记录角色、配置模型名、耗时、状态、错误码和供应商报告的 usage。

转账、账单和资金计划的最终业务摘要由确定性事实渲染。模型叙述单独标为辅助说明，不覆盖事实，也不再当作下一层复核的权威证据。失败保留 `mode:model` 和错误记录，不能伪装成脚本成功。

复核的 `approved` 只表示提案足以进入后续人工确认和 Core 鉴权流程，不授予金融操作权限。`diagnostics` 记录领域结构化建议是否存在、是否要求澄清，以及复核原始决策和确定性检查后的有效决策，用于区分提案遗漏、主动否决与调用失败。

## 持久化与验收边界

最近一次完成的计划及其事件、事实证据、调用统计可在刷新后恢复；动作始终读取最新状态。完整聊天文本、长期会话图状态和任意中途图恢复仍未实现，PostgresSaver 中断恢复仅有独立 PoC。

固定评测保留脚本基线与真实调用两套结果，用确定性断言校验金额、收款人、澄清、预算拒绝、原始证据与调用完成性。源文件指纹和原始规划结果写入 JSON，供应商输入 usage 为 0 不代表实际无输入或免费。真实结果和浏览器验收记录见 `phase2-verification.md`。

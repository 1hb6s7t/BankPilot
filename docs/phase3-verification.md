# BankPilot 第三阶段实现与验收记录

日期：2026-10-22（Asia/Shanghai）。本阶段交付联系人别名确认保存、银行卡状态/挂失/解挂、订阅查询/商户取消/银行扣款拦截，并接入现有多 Agent 规划、独立复核与计划恢复。业务仅作用于本地合成银行和合成商户。

## 已交付行为

| 模块 | 可操作路径 | 实际约束与结果 |
|---|---|---|
| 联系人 | 选择合成收款人 → 输入别名 → 生成候选 → 明确确认 | 确认前不保存；确认后按用户保存，可供自然语言转账解析。别名冲突、跨用户访问被拒绝；保存不转账 |
| 卡片 | 直接查状态；准备挂失/解挂 → 核对卡名与尾号 → Passkey | 两种变更均为红档，普通确认不能执行。绑定资源版本，挂失影响卡片扣款能力，不取消商户合同 |
| 订阅查询 | 准备查询 → 黄色确认 → 读取列表 | 初始页面隐藏明细。服务端授权默认 5 分钟，管理动作默认 10 分钟；查询过期后重新确认，成功动作重试不续期 |
| 商户取消 | 已授权查询 → 明确商户 → 取消候选 → 黄色确认 | 仅支持的合成商户可取消；商户状态改变，银行扣款限制独立，既不退款也不增加余额 |
| 银行扣款拦截 | 已授权查询 → 选择订阅 → 拦截候选 → 黄色确认 | 只改变银行扣款限制，商户合同可仍有效；不支持商户在线取消时不会偷偷改成另一操作 |
| 规划与恢复 | 自然语言提出卡片/订阅请求 → 领域节点 → 独立复核 → 待确认动作 | 模型不能执行或批准。最新计划恢复时重新取得动作状态，管理动作完成后流程展示“操作已完成” |

接口、状态和复用分类详见 [phase3-contract.md](phase3-contract.md)。卡片、订阅及别名操作在同一数据库事务中写业务状态、授权、回执和审计；它们是同步本地合成操作，未冒充真实外部商户网络调用或异步银行执行。

## 开发协作与复用

延续此前按难度分配的三个并行子 Agent：

| 分工 | 模型 | 选择理由与交叉检查 |
|---|---|---|
| 管理执行核心、授权/版本/幂等与数据隔离 | GPT-6 Astra，高推理 | 状态与授权错误影响范围大；实现后独立复核规划和 API 边界 |
| LangGraph 领域编排、确定性意图解析、模型契约及固定样本 | GPT-6.1 Sol，高推理 | 需要联动现有六领域、独立 reviewer 和严格输出契约；接受核心 Agent 的否定/错卡名复核 |
| 联系人/卡片/订阅页面、共用确认卡和阶段契约 | GPT-6 Luna，高推理 | 输入输出契约明确，适合独立实现页面；主 Agent 检查接口接线和实际浏览器行为 |
| 集成与最终验收 | 主 Agent | 冻结共享类型，接 API/Passkey，补 API 与浏览器测试，运行真实模型评测并汇总失败与修正 |

这是开发协作分工。产品运行时仍使用用户指定的同一个云端模型 `DeepSeek-V4.1-Flash-1017-New`，按需并行领域调用，再运行独立复核；没有宣称产品已经具备多供应商自动路由。

本阶段直接沿用 LangGraphJS、Better Auth、SimpleWebAuthn、Hono、Zod、React、PostgreSQL。适配现有动作契约、会话、WebAuthn 验证器、提案恢复、工作台确认卡与评测器；新增的是比赛所需的联系人命名空间、卡状态、订阅双状态、查询授权和业务版本规则。未新增运行时依赖，未引入完整核心银行或计费平台。开源筛选与源码证据沿用 `research/2026-10-22/`，本阶段不会把参考项目未提供的银行业务能力标为可直接复用。

## 浏览器验收与失败记录

使用 Chromium、真实 Hono API、PostgreSQL、pg-boss Worker，以及实际云端模型。WebAuthn 使用 Chromium 虚拟认证器生成真实密钥和签名，再由服务器验证，没有伪造服务端验证成功；未验证用户实际设备上的生物识别。

三个业务流程均完成通过，运行记录按真实顺序保留：初次全量运行 1 通过、2 失败；修复后定向复跑管理与转账 2/2 通过，而非宣称一次全量无失败。

| 流程 | 最后结果 | 实际断言 |
|---|---|---|
| 账单与资金保护 | 通过，约 1.6 分钟 | 原账单证据跳转、预算编辑确认、保护金额 5500 元时拒绝 4000 元支出、刷新恢复、手机布局 |
| 联系人/卡片/订阅 | 修正后通过，33.2 秒 | 别名先候选后保存；Passkey 挂失/解挂；查询确认前无列表；真实模型提出取消；商户取消/银行拦截分开；重新授权、状态恢复及手机布局；余额始终 800000 分 |
| 转账与恢复 | 定向复测通过，56.0 秒 | 600 元黄档、累计超过 1000 元红档、弱确认不能执行、真实签名、记账后超时进入 UNKNOWN、刷新后查单、两条银行记录且最终余额 680000 分 |

另对最后的流程汇总展示修正做了浏览器只读恢复检查：已完成管理计划显示“操作已完成”，管理动作回执为成功；进入订阅页仍隐藏列表并要求新查询确认。没有为此额外调用模型。

重要失败及处理：

1. 新浏览器测试最初匹配到两个 `role=status` 元素，属于测试定位不够精确；已限定管理动作内的注册提示。
2. 初次管理全流程在重新授权处失败：已有订阅列表时按钮被条件渲染隐藏。已补齐列表展示期间的入口，并确认新候选生成后旧列表立即隐藏、确认后重新显示。
3. 初次转账流程的 reviewer 返回 `MODEL_SCHEMA_INVALID`。系统保留失败并拒绝生成执行提案，没有自动降级或授权。未取得被拒绝输出的具体字段，不能断言是哪一字段错误；保持严格校验，定向复跑成功。这仍是云端输出稳定性限制。
4. 初次资金保护流程出现三次 `MODEL_HTTP_502`，各领域在既有重试上限内恢复，reviewer 正确拒绝资金不足计划。业务流程通过不等于每次供应商尝试均成功。

失败原始计划保留为 [转账 schema 失败](../evals/results/2026-10-22-phase3-browser-attempt1-0.json)、[管理首轮计划](../evals/results/2026-10-22-phase3-browser-attempt1-1.json)、[资金保护及 502 重试](../evals/results/2026-10-22-phase3-browser-attempt1-2.json)。最终成功计划、当前业务状态、源码指纹和只读恢复检查另存于 [browser-final.json](../evals/results/2026-10-22-phase3-browser-final.json)。原计划中的待确认状态属于创建时快照，最终业务状态记录在单独的 current 字段。

## 复核发现与修正

- 新别名不能写回全局合成收款人种子表：新增按用户保存的别名表，API/规划合并当前用户视图。
- 后置否定和“不再取消”等表述可能形成错误候选：补齐保守否定处理和 23 项回归。
- 单卡情况下的陌生显式卡名不能默认为现有卡：只有通称、匹配名称或尾号可匹配，冲突要求澄清。
- 管理动作刷新时不能丢失确认所需的商户/金额：仅在该动作绑定的原查询授权有效时保留冻结明细，过期后隐藏；新授权不会复活旧动作。
- 已完成管理动作需进入计划汇总，不能再显示“暂无可执行动作”；汇总也区分全部完成与部分完成。

本地 `.env` 权限为 0600，受 Git 忽略；导出文件扫描未发现已配置的模型凭据。报告不含请求头或 `.env` 内容。

# G9H：账单领域紧凑结构输出评测预登记

2026-10-25，云端运行前协议。G9H只改变账单领域的有类型输出契约及该契约所需的产品接线；账单确定性分析、原用户请求、其它领域、复核与资金权限边界仍须原样接受测试。G9G的36例已知回归和12例开发知情补充样本已经暴露，G9H两组均不是盲测。新结果存入独立目录，不改写G9G报告、评分器或标签。

## 诊断事实与待验证假设

G9G已知组 `g9-card-06` 有两个账单领域尝试：`max_tokens=4096`，均为HTTP 200、`finish_reason=length`和`MODEL_OUTPUT_TRUNCATED`；各自报告的输出token为4096、reasoning token为2923和3248。可见输出仅存长度及摘要，没有保存账单域原文，因此不能声称原文重复、具体缺了哪些字段，或断言截断由某一句指令单独造成。此例语义和卡领域完成，账单失败后没有独立复核；该事实不能视为账单回答已通过。

当前账单输入已有服务端 `analyzeBills` 的确定性结果，而领域输出要求返回 `summary`、`findings`和`evidence`。产品接线随后以确定性 `scriptDomain` 替换这些财务事实，只保留模型解释为单独证据。紧凑账单契约可能减少需要生成的可见结构内容；是否减少截断、是否保全查询范围与证据，由同版完整运行验证。输入schema、指令和分析中存在相邻事实或约束的重复，但没有原始账单输出，不能把静态冗余直接定为截断原因。

## 唯一产品变量和固定条件

本轮受控产品改动限定为账单领域的有类型输出契约及其接线，包括账单专属的原问题文本和结构化可信facts：模型输出只表达该契约要求的最小核对信息；账单金额、月份、筛选、覆盖状态、交易引用由服务端确定性分析提供并在独立复核中核对。任何契约缩减都不能弱化复核拒绝时的隐藏规则，或把未知筛选改成整月汇总。其它领域的字段、账单分析算法、权限与动作语义不得为得分做个例调整。先跑纯测试、全仓隔离数据库测试和受控浏览器，再由冻结源码运行云端。

沿用G9G默认provider指纹：`thinking`与`reasoning_effort`均省略，`json_object`输出模式；不增删模型参数，不变温度、60秒provider超时、180秒单例截止、每次至多2个HTTP尝试与1次结构修复。保持G9_LIMITS每例请求输出上限32768、语义阶段4096以及现有按实际领域数均分的预算算法；不得为账单单独加cap、转借其它阶段预留或按实际usage退款。所控制的代码差异限定为上述账单契约接线；非同期的供应商随机性和后台变化仍可能影响结果，单次顺序运行不能作因果归因。

## 冻结、顺序和先验门禁

冻结manifest绑定原始G9与质量组父manifest、36/12例的原输入和原标签摘要、G9G当前标签摘要、provider指纹、G9_LIMITS、协议hash、评测文件hash和产品源码快照。每次运行前后核对所有冻结文件与快照清单。只执行 `default-known` 36例，再执行 `default-quality` 12例，各自一次独立首次结果；不自动重跑全组，不以失败例重试回填。质量组必须读取本轮已完成且`validRun=true`的已知组报告，并重算每例三份score、三份汇总、相邻case/attempt/semantic/bill日志及输入、标签、source绑定。有效的业务失败可以进入下一组；记录缺失、源码漂移、预算超限和评测无效则阻止质量组。

两组均逐例串行，产品内部领域保持并行及独立复核。每例保留原G9、G9E、G9G三口径score与独立分母；业务未通过、模型截断、不可评、无usage、日志未闭合分别列出，不将不可评记为通过。旧G9G报告不回填新score或结果。

## 可审计尝试与账单可见输出

每次HTTP尝试在请求前fsync持久化开始记录，结束记录包含role、attemptId、状态、HTTP状态、错误码、`max_tokens`、可得usage和结束时间。保存每个语义尝试的可见结构输出到 `semantic-extraction.jsonl`，并新增每个账单领域尝试的可见结构输出到 `bill-domain-output.jsonl`；两者均绑定case序号、attemptId、role、状态、输出长度与SHA-256。按provider观察接口的64KiB UTF-8上限完整存放可见字符串，超限则只记`size_limit`和摘要，不截断拼接。账单即使HTTP失败或结构截断，也必须有与派发尝试一一对应的观察记录；缺失、重复、摘要不符或持久化失败使本轮无效。若全组没有账单尝试，空账单sidecar仍应存在并可核对为零。保存的仅为合成样本可见结构输出，不含reasoning全文、请求header或API key；reasoning token统计是provider的计数，不是账单正文内容。

运行期间逐例写入并同步case日志，尾记录保存三份汇总和有效性。缺失usage不填零；账单sidecar可用于排查可见结构，但不能重构隐藏reasoning或证明其因果路径。

## 判定与后续实验

主要比较36与12组的三口径可评数、通过数、截断数、尝试与token使用，以及账单和复合只读案例的完整范围、月份、金额和证据绑定。任何账单复核拒绝必须继续隐藏未批准的答案，所有管理/资金动作保持独立授权。当前G9G已知组当前契约为35/36，唯一不可评为`g9-card-06`；G9H能否改善需看冻结后完整首次结果，不凭单例成功宣称整体通过。

若另测账单加权预算、`reasoning_effort`或其它provider参数，必须另立版本和协议，分别改变一个变量并重新跑完整36→12，不与本轮紧凑契约结果合并为同一实验。已知/开发知情48例、受控浏览器和新未见样本属于不同证据层，不互相替代；G9H结果本身不等于产品发布验收。

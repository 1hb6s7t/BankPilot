# G8F stage-recovery independent review checklist

Status: **G8F frozen automated suite 1417/1417 and controlled-browser suite 4/4 independently reviewed**. This is scoped orchestration/recovery evidence, not live-provider or model-quality acceptance. The existing semantic-recognition recovery scope and G8E results remain distinct.

## Required behavioral contract

Treat each domain proposal and the reviewer as durable planning stages. If a transient provider failure interrupts a plan, persist a retryable failed command, retain only verified successful stage outputs, and on explicit retry execute only the unfinished stage work. Domain business rejection, deterministic validation rejection, and a valid reviewer `approved=false` are completed stage outcomes; they must not become service failures. A reviewer may run only against the complete, stable, validated set of domain outcomes for the current plan.

For model-proposal work, distinguish: (a) transport/service failure that may be retryable, (b) malformed output or a candidate that violates the role/amount/spec contract, which is a nonretryable system/candidate failure after bounded repair, and (c) valid business outcomes that complete normally. Examples of valid business outcomes include deterministic funds insufficiency, a genuine clarification because required user information is absent, and valid reviewer `approved=false`. A schema-valid model candidate that changes the resolved amount/payee, returns the wrong role, omits a required structured suggestion, or changes a deterministic management/investment/goal spec is not a business rejection and must not be represented as a normal completed rejection or user clarification. Do not infer these classes from `PlanResult.rejected`, empty proposals, or a single diagnostic status alone.

## Black-box acceptance scenarios

Run each scenario with both planner checkpointing **disabled** and **enabled**, unless the case explicitly targets checkpoint machinery. Use isolated test identities and synthetic provider adapters. Assert provider call sequence/count by role, per-role outcome, durable stage-cache key/digest, checkpoint identity/pointer where applicable, command status/retryability, persisted proposal/result, model attempt journal, and side-effect counts.

- [ ] **Parallel fast failure + slow success, checkpointing off.** Start two distinct domains in parallel. One returns a retryable service error quickly; the other blocks and later returns a valid proposal. Do not publish terminal failure or release the command while the sibling is still able to commit. After both settle, persist exactly the successful sibling result and the failed sibling state. Retry the same command: the successful sibling is not called again, the failed sibling is called once, and one reviewer call follows only after every required domain has a stable final outcome. The final result has one proposal per role, deterministic role ordering, no duplicate events, and no missing or duplicated model runs.
- [ ] **Parallel fast failure + slow success, checkpointing on.** Repeat the same schedule with a real configured checkpointer. The retry must resume or safely transfer the exact trusted checkpoint lineage and merge the settled successful role once. Neither a delayed old graph task nor a resumed task can append the same proposal/event/run twice. A stale or untrusted checkpoint must fail closed without changing the stage cache or creating an action.
- [ ] **Inverse completion order and multiple failures.** Make the slow branch fail while the fast branch succeeds; then make two branches fail with different codes and timings. Verify outcomes are associated with role/stage identity, not arrival order or shared mutable arrays. Retry only failed roles; successful roles remain unchanged. A later transient error must not overwrite an earlier permanent candidate/validation failure without an explicit policy.
- [ ] **Stage-cache identity and cross-command isolation.** Prove cache entries bind at least user, command/root command, revision, current lease or trusted lineage, plan/input digest, graph/state/schema version, semantic/finance input digest, orchestration mode, role, and stage-contract version as applicable. Same text under another command, another account/user, a new revision, changed catalog/funds/bill facts, changed role contract, or incompatible graph version must not reuse proposals. Mutation of cached payload, role, digest, version, or source input must be rejected before reviewer or side effects.
- [ ] **No checkpoint mode is still durable.** With checkpointing disabled, kill/rebuild the API process after one domain stage has durably succeeded and another failed. Explicit retry must recover successful stage cache from the command journal, not from process memory, and continue only the failed work. If the implementation intentionally cannot recover a specific boundary without checkpoints, it must fail explicitly and preserve side-effect safety rather than silently rerun all models.
- [ ] **Checkpoint and stage cache cannot contradict each other.** For checkpoint mode, inject a valid stage cache with an older checkpoint, a checkpoint with no matching stage-cache row, mismatched cache/checkpoint digests, copied checkpoint from another command, stale checkpoint head, and checkpoint pointer transfer failure. The system must either prove both represent the same trusted prefix or stop before provider calls/reviewer/actions. Never trust LangGraph checkpoint contents alone when their journal binding disagrees.
- [ ] **Budget exhausted but cached work remains.** Reserve/exhaust the command’s remaining provider output budget after a domain failure while retaining successful domain outputs. Retry must still be allowed to run deterministic cache validation/merge and complete stages that require no provider call. It must not fail prematurely merely because the cap is full if no new call is needed. If any unfinished provider call is required, reject before dispatch with a budget-specific nonretryable failure; do not refresh the cap, issue a zero/over-cap request, or misreport cached stages as new attempts. Repeat with reviewer output as the only remaining provider stage.
- [ ] **Reviewer binds the full stable domain result set.** Supply mixed-role results and vary one component at a time: accepted proposal content/evidence, rejected business outcome/reason, deterministic rejection, domain role/status, role ordering, source references, planner version, and the final set of expected roles. Reviewer input must be derived from the exact complete stable set and its digest. Any change invalidates a cached reviewer result. The reviewer must not run while any required role is failed/in-flight/missing; it must run once after repair. A reviewer `approved=false` is a completed normal outcome and must not trigger reviewer retry by itself.
- [ ] **Business result classes stay distinct.** Separately exercise (1) deterministic funds insufficiency, (2) a legitimate missing-slot clarification from semantic intent, and (3) valid reviewer `approved=false`. Each is a completed business outcome with its expected result/clarification, no false infrastructure retry, and no unauthorized action. Reviewer denial preserves findings and effective approval false; insufficient funds retains the deterministic shortfall; clarification asks only for missing facts.
- [ ] **Permanent candidate/contract error versus service failure.** Separately inject retryable 5xx/timeout/network errors, permanent authentication/refusal errors, malformed JSON/schema/tool outputs, and schema-valid but invalid domain candidates: wrong role, amount/payee mismatch, missing required structured suggestion, or management/investment/goal spec mismatch. Candidate/contract violations are nonretryable planning/system failures after bounded repair, not completed business rejections or user clarifications. Verify stable code, phase, retryability, proposal/action absence, failed-attempt history, and no same-command dispatch after permanent failure. A valid business rejection above remains a normal completed result. Exhausted structural repair does not loop across command retries unless a separately bounded policy explicitly allows it.
- [ ] **Lease race: failure writer versus success writer.** Hold an old lease’s failing branch while a new explicit retry takes over and completes successfully; then release the old failure write. Repeat with old success arriving after the new lease writes failure, and with simultaneous complete/fail transactions at lease expiry. Exactly one current lease may publish the terminal status, stage-cache delta, proposal/result, and assistant message. Losing writes must be fenced by lease token/status/revision, must not append stale failures, and must not erase or replace the winner’s cache/checkpoint.
- [ ] **Attempt history is neither duplicated nor lost.** Across provider-internal retries, parallel domains, reviewer attempts, command retries, checkpoint resume, process restart, and one unknown/lost response, compare durable attempt rows to actual dispatched calls. Keep stable invocation identity for one stage invocation, distinct attempt identities per request, no synthetic attempt for cache reuse, no duplicate imported checkpoint runs, and no lost unknown attempt. Preserve original timestamps, role, phase, cap and usage/unknown state. Public `modelRuns` and attempt journal must follow the contract; do not silently concatenate checkpoint history with journal history twice.
- [ ] **Proposal/action/result replay compatibility.** If proposal/action creation already began, retry must preserve deterministic child command IDs and create at most one effect. A complete command replays the stored result and current action state without model calls. A business rejection or reviewer denial also remains complete on retry. Historical completed rows remain immutable and are not reinterpreted just because new stage-cache versions exist. Test proposal saved/action absent, action committed/result absent, and result committed/client response lost separately.

## Required assertions and evidence

For every scenario capture a redacted before/after journal view: command/root/revision, lease token hash, state and retryability, graph/checkpoint pointer, each cached stage key/version/digest/status, ordered model attempts and `modelRuns`, provider calls by role, proposal/result digest, assistant messages, and action counts. Requested output caps and actual usage must remain separate; missing usage is unknown, not zero. Demonstrate at least one adversarial schedule with deferred promises rather than relying only on fixed sleeps.

Do not call a cached stage “successful” solely because a checkpoint contains a value: independently validate the stage envelope, identity, version, and digest before it can feed another stage. Do not claim business acceptance from successful recovery of orchestration; semantic correctness, proposal quality, reviewer correctness, browser behavior, live-provider availability, and action execution remain separate outcomes.

## Existing project mechanisms to adapt

- `apps/api/src/plan-runner.ts` already has command lease claims, current-lease assertions, retry/failure persistence, and final-result fencing; reuse those production boundaries in black-box integration cases.
- `apps/api/src/planning-journal.ts` already persists semantic input/result snapshots and provider attempt reservations. Review how G8F binds new per-domain/reviewer cache entries to this journal and cumulative budget.
- `packages/agents/src/index.ts` currently fans out parallel domain nodes and then runs the reviewer; its catch paths and `modelRuns` aggregation are natural observation points for fast/slow branch fault injection.
- Existing test fixtures include `tests/g8e-recovery-api.integration.test.ts`, `tests/g8e-planning-journal.integration.test.ts`, `tests/g8e-runner-observation.test.ts`, `tests/conversations-process-recovery.integration.test.ts`, `tests/planner-checkpoint-process-recovery.integration.test.ts`, and `tests/agents-checkpoint-fencing.test.ts`. Adapt their isolated DB schema, deferred provider responses, process crash, and lease-fencing patterns; do not weaken historical assertions.
- Existing Zod result contracts and PostgreSQL journal/lease primitives should be extended or versioned in place. Do not add a new queue, checkpoint store, or open-source dependency without a separate architecture decision.

## Reviewer disposition template

For each case record: **pass / fail / not run**, exact test/evidence path, source-manifest identity, provider call sequence, cache/checkpoint digests, command status, and any limitation. Keep every item open until its dedicated evidence exists. Report checkpoint-disabled and checkpoint-enabled results separately. No combined “recovery passed” conclusion may hide a failed mode or an untested scheduling window.

## Read-only implementation review (2026-10-23)

The current G8F source now includes `stage-recovery.ts`, `planning-failures.ts`, per-command `stage_results`/`stage_history`, and stage journal wiring in the planner runner. Static review found the key safety properties represented in code: every saved stage is bound to the frozen planner-input digest and graph/schema versions; load checks the dependency digest and result schema; writes and failure records use the current running lease transaction; the planner waits for in-flight branches before settling; and permanent failures take precedence over transient sibling failures. The domain/reviewer candidate contract failures thrown by the stage wrapper are nonretryable, while provider 5xx/timeout/network/deadline codes remain retryable. This is source inspection, not an execution finding; Root separately reports the first 11 API cases passed and Astra is continuing isolated PG/checkpoint verification.

The previously reported failed-command `failure.modelRuns` observability gap is **closed for the tested cases**. Before persisting a planning failure, `plan-runner.ts` reads same-lease stage journal history and replaces (rather than appends to) the selected failure's run list with semantic runs plus aggregate stage runs; on journal-read error it retains the original failure. The final API assertions verify semantic plus bills/transfer role attempts in the mixed failure schedules, and the final frozen suite passes 1417/1417. A stale lease cannot write stage history in the journal fencing test. Remaining interleavings are not exhaustively covered.

One separate, deterministic evaluation compatibility gap remains for a later quality-evaluation phase. `scripts/evaluate-g7.ts` catches any planner throw other than `ModelAttemptPersistenceError` as `EVAL_RUN_ERROR`; it builds returned-plan run totals and `latency.casesWithCalls` from `result.modelRuns`. The new stage runner can throw `PlanningStageFailure` after real domain/reviewer attempts. Its independent attempt JSONL can still show dispatched calls, but the evaluator's model-call totals/status codes and cases-with-calls latency omit them when there is no `PlanResult`. `scripts/evaluate-model.ts` and `scripts/evaluate-ablation.ts` similarly use generic `EVAL_RUN_ERROR` handling and aggregate returned results. Before G8G or any new live quality run, adapt those scripts to preserve typed planning failure (phase/stage/code/retryability), join ModelRuns/attempts from the independent journal without double-counting, and compute call/latency denominators from observed dispatch attempts rather than `result.modelRuns` alone. This is a report-protocol compatibility issue, not evidence that current G8F stage execution is unsafe; do not run live quality until addressed and separately frozen.

Remaining unverified areas include cache-only continuation at an exhausted cumulative budget, all possible checkpoint/cache disagreement modes, every lease/process crash interleaving, and candidate-contract cases outside the targeted transfer fields. The controlled browser cases passed 4/4, and no live quality evaluation was run for G8F. The parent-provided local-upgrade evidence reports unchanged DB/business history summaries across an idempotent migration plus healthy API/web checks; this reviewer inspected the evidence file but did not connect to those services. A distinct evaluation-script compatibility gap remains open: `evaluate-g7.ts`, `evaluate-model.ts`, and `evaluate-ablation.ts` still need typed `PlanningStageFailure` diagnostics and attempt-journal aggregation so dispatched calls on a failed plan are not reported as zero calls/latency. This must be fixed before another quality run; G8F’s 1417 automated checks do not establish model quality or close that gap.

# G8K 聊天分页与独立恢复事项验收

日期：2026-10-24，上海时间。本轮接续 G8J 的两个明确缺口：消息页仍附带整段会话的全部命令，以及聊天列表只返回最近 100 个。工作范围仍是本地合成银行；云模型质量和比赛最终交付单独验收。

## 实现与复用

| 模块 | 本轮结果 | 复用边界 |
|---|---|---|
| 聊天列表 | 默认 30 条，按不可变创建时间和 ID 分页；增加按 ID 读取聊天 | 复用 PostgreSQL keyset 查询与现有归属检查。游标锚点时间在数据库内比较，不经 JavaScript 毫秒截断 |
| 消息历史 | 默认 50 条，只关联本页消息涉及的 command 与 clarification；单独返回轻量 latestCommandId | 复用 G8J 历史合并、缺页补齐与按 ID 详情。assistant 结果页也能关联原 command |
| 恢复事项 | 默认 20 条摘要，独立前后页、刷新与回到最新；包含 pending、running、failed 和 waiting clarification | 复用现有命令/澄清状态；摘要不返回完整 planningInput、result 或 modelAttempts，不自动执行恢复 |
| 数据库快照与索引 | 每次页面读取保持 REPEATABLE READ READ ONLY；增加列表创建序、未完成命令与待澄清索引 | 继续使用 pg 与共享事务 helper；没有新数据库、队列或分页依赖 |
| 浏览器会话恢复 | 首屏只读列表一页，较早选中聊天按 ID 恢复；分页失败保留当前页并可重试 | 复用 React、assistant-ui、账号/会话 generation gate；没有自动扫描全部列表 |
| 澄清关闭证据 | 回答和取消在同事务递增父命令版本；成功响应立即更新客户端已知澄清状态 | 自建少量业务状态合并，复用原 CAS 与幂等契约；不猜测 command stateVersion，不改交易授权 |

依赖与锁文件未升级。金额、风险、授权、账本及回执仍由确定性 Core 控制，恢复列表不能执行任何银行动作。

消息页返回的**关联记录数**受页面大小约束，但本页 command 仍包含完整结果和调用记录，因此不把它描述成严格的响应字节上限。恢复摘要另外限制请求预览和问题文本长度。查询使用未完成/等待索引，也不代表任意规模下数据库扫描或延迟恒定。

## 分页与状态约束

游标包含版本、种类、归属用户、可选会话以及锚点 ID。服务端检查结构和长度，再按当前用户/会话验证锚点；混用列表/恢复游标、借用其他用户或会话的游标都被拒绝。恢复锚点即使已经完成仍可用于继续翻页。每页是当次数据库快照；跨多次翻页不是长期冻结快照，新出现或新失败的事项通过回到最新页刷新发现。

消息页不再承担“找到所有未处理请求”的职责。恢复事项独立分页，即使原用户消息在最新 50 条之外，也仍可查看、继续原命令或补充原澄清。读取详情会先核对当前状态；只有明确点击继续/重试才进入原命令的规划入口。

对待恢复命令缺少可验证原用户消息、或序号不安全的异常数据，服务端返回 `409 RECOVERY_REQUEST_SEQUENCE_UNAVAILABLE`，并给出可定位请求信息；不会猜序号或静默忽略。正常接收路径的命令和原消息原子保存。该错误不是自动修复损坏数据的能力。

客户端保留明确选中的旧计划，恢复页只管理本页事项，不直接替换计划。较新 command 版本、已知终态回执和澄清版本抵挡迟到的历史或索引响应。聊天切换清空当前缓存并取消旧 generation，账号切换另有 owner/session 隔离。

## 实际发现并修复的澄清窗口

独立复核发现：取消已返回成功，但紧接的父命令详情 GET 失败时，客户端丢弃了成功取消响应，仍保留旧 waiting 状态。把真实旧恢复响应延迟到该时刻，会继续显示“继续补充/取消”；服务端仍拒绝旧版本再次提交，因此没有重复办理，但界面会误导用户。

[真实红测](evidence/g8k-browser-2026-10-24/clarification-read-failure-red/report.json)保存了取消 POST 200、后续读取 503、旧恢复响应持有期间界面仍残留请求的失败。修复后，取消直接保留服务端返回的 cancelled/version；回答收到匹配父请求的 accepted successor 后，依据该次已提交 CAS 保留 resolved/version 和 successor ID，再继续读取详情。独立澄清证据也用于规范化迟到的完整 command，而不仅过滤恢复摘要。

[同场景定向绿测](evidence/g8k-browser-2026-10-24/clarification-read-failure-fix/report.json)通过。最终浏览器还验证了实际回答 POST 202 后的同类读取故障：只接收一次回答、保留同一父子链、产生一笔待确认提案，没有付款或授权。

最终十条流程覆盖：

1. G8J 的 159 条消息、原 307.50 元转账回执、7692.50 元余额以及刷新/重登恢复。
2. 首次/旧页读取失败可重试，225 条消息缺页补齐，最新页之外的旧 pending 可找到。
3. 迟到账户旧快照不能把完成后的余额覆盖回 8000 元。
4. 确认 POST 已提交但 HTTP 响应丢失，通过只读恢复，授权 POST 仍恰好一次。
5. 126 个聊天全部可分页找到；失败页使用原游标重试；较早选中聊天重登后精确恢复，首次不会遍历全部聊天。
6. 45 个旧请求与 240 条归档消息：最新消息页关联 command 为 0，但恢复页能找到最早的 pending、failed、waiting；显式重试沿原 command 产生 317 元待确认提案，未付款。
7. 真实旧恢复响应不能复活已完成请求，切换聊天后不能回流旧事项。
8. 较早澄清取消后，真实迟到 waiting 响应不能恢复入口。
9. 取消成功、后续详情/历史读取 503 时，仍保留关闭证据，刷新后只有一条取消记录。
10. 回答已接受、后续父详情/历史读取失败时，仍关闭父澄清；旧索引不能复活它，原子链最终只产生一笔 318 元待确认提案。

初始 [5/7 浏览器记录](evidence/g8k-browser-2026-10-24/attempt-1/report.json)保留：两项是测试假设错误——Vite/React StrictMode 可启动一次随后废弃的重复首屏 GET，以及测试自行填写的问题文案不同于真实澄清生成结果。修订后仍要求首屏最多两个同一页请求、无 cursor 自动扫描、每页上限 30；问题文本改为核对实际澄清。第二轮 [8/8](evidence/g8k-browser-2026-10-24/attempt-2/report.json)是后来新增读取故障窗口之前的结果，不替代最终 10/10。

后端第一轮 [62/63](../evals/results/2026-10-24-g8k-pagination-attempt-1.json)是测试 JSON 数组参数未序列化；修正 fixture 后定向通过。随后四项真实边界红测为 [11/15](../evals/results/2026-10-24-g8k-pagination-boundary-red.json)，涉及 orphan 恢复和澄清父版本，修复后还验证了取消/回答回滚及幂等；这些失败没有覆盖成绿色。

## 分工、云状态与剩余范围

接续运行开始时，旧 API、Worker 和 Web 进程已不存在，PostgreSQL 仍健康。验证完成后幂等补齐聊天迁移并启动 G8K，没有运行 seed 或重置业务数据。当前 [5178 页面](http://localhost:5178/) 与 API 健康检查均为 200，见[运行核对](evidence/2026-10-24-g8k-runtime-refresh.json)。48 张原表中 46 张摘要一致，账户、回执、会话、消息及全部 97 个原命令保持；两张理财 action/outbox 表在后台查单时有更新，没有逐字段等价的证据，因此不声称所有表不变。

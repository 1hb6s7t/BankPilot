## 用户能够感知的修复

旧聊天中的“查看计划”现在按明确的原 command 展示，翻页与轮询不会把它换成最新计划。新提交和重新进入聊天恢复默认的最新请求选择；用户可再次打开旧计划。计划详情从 Core 读取动作状态，存储的历史提案不会把相同动作的成功回执覆盖回待授权状态。

历史合并会识别消息序号中间的缺口。最新页刷新一次跨过 50 条以上消息时，继续加载会先补最近的缺口，再向最旧页推进；第一次读取失败后的手动重载也会恢复分页入口。空页或重复页没有推进时保留已加载内容并提示重试。原文按消息 ID 保留，不通过读历史重跑规划。

浏览器实际覆盖一段 **159 条消息**：第一笔 307.50 元转账执行成功后，添加 155 条合成归档消息，再创建第二笔 600 元计划。两计划使用相同创建时间仍按用户消息序号排序；选中旧计划、补齐全部消息、刷新及退出重登后都能读取原回执。终态只有一笔提供方转账、两条双边分录和一个授权证明，余额 **7692.50 元**，第二笔仍未授权；只读恢复没有新增模型调用或付款。

第二条浏览器流程验证首次历史 GET 失败、旧页 GET 失败、115 条已加载消息之后再新增 110 条，最终 225 条无重复地补齐；随后把一个原 pending 请求留在最新页之外，刷新和切聊天仍能找到“继续原请求”。该流程最终保存 281 条消息，模型调用 0，没有自动执行 pending 请求。

验收中另发现并实际复现了两个账户展示问题：

- **迟到的旧 Dashboard 覆盖新余额。** 真实付款和原回执已经完成，旧读取返回后却将页面从 7692.50 元覆盖回 8000 元。账户概览现只采纳完整服务端快照；同账号读取单飞，成功写入或详情先观察到终态时提高刷新屏障，旧在途响应不再满足该屏障，随后补读完整快照。动作详情可以先展示回执，但不能修改账户快照的轮询依据。账号切换另有 generation 与读取 epoch 两层隔离。
- **授权成功但 HTTP 响应丢失后，页面不再刷新。** 测试让真实确认请求完成后中断响应。修复后保留原错误提示，仅通过 GET 恢复余额和回执。浏览器确认授权 POST **恰好 1 次**，没有自动重发授权。转账确认、取消、查单、顶层 Passkey 注册的异常分支沿用这条只读刷新路径；本次真实丢响应场景只覆盖转账确认，其他领域卡片的未知写入响应还需继续验证。

计划详情的刷新、交易后的全量刷新及 Passkey 注册数量更新共用现有机制。理财卡和生活目标内嵌卡补齐注册成功后的父级刷新回调；没有改变授权规则。

## 持久化、查询与复用方式

| 模块 | 本轮处理 | 复用或自建边界 |
|---|---|---|
| 聊天、调用日志、规划完成/失败、检查点事务 | 适配 G8I 的共享连接与事务生命周期；只读历史保持 REPEATABLE READ READ ONLY | 复用 pg/PostgreSQL 和现有 helper；不自动重试未知提交，不改业务租约与预算规则 |
| WebAuthn 验证计数器 | 复用共享事务，提交成功后才能签发动作绑定的 STRONG 凭据 | 保留 SimpleWebAuthn；8 项单测模拟签名结果，只验证事务顺序；真实签名由独立浏览器流程验证 |
| 历史查询 | 批量关联用户请求序号和澄清，移除逐 command 读取 | 160 条实际接收请求、4 页各固定 **6 次 SQL**（含 BEGIN/COMMIT）；[37 项集成报告](../evals/results/2026-10-23-g8j-history-integration.json)包含 6 项新增用例 |
| 命令状态与游标 | `requestSequence` 决定顺序；数据库 trigger 递增 `stateVersion`，JSON 用十进制字符串 | 自建业务版本契约，前端用 BigInt 比较；不安全消息序号明确拒绝并回滚，不静默舍入 |
| 页面历史与账户合并 | 复用 assistant-ui、React、现有 GenerationGate；增加选中计划和完整账户快照协调 | 自建少量业务状态逻辑，保留 Core 为金额、授权、执行与回执权威 |

依赖及版本均保持不变，延续既有开源复用决策与锁文件。没有新增模型供应商、数据库、队列或聊天服务。

**查询次数固定不等于响应大小有界。** 当前每页仍返回整个会话的 commands 与 clarifications；列表仍只返回最近 100 个聊天。没有为了性能而截掉旧 pending、failed 或 waiting 项。下一阶段需将有界时间线与分页的恢复事项索引拆开，保留旧计划按 ID 读取；长列表渲染和更大规模容量也尚未验收。

## 八个实际数据库故障窗口

1. 接收用户消息/command 的 COMMIT 前终止本测试 backend：消息和命令原子回滚，同一 clientMessageId 可重新接收。
2. 接收 COMMIT 已持久化后丢失回应：同 ID 重放返回原命令，只有显式继续才执行规划。
3. 最终 result 与助手消息 COMMIT 前断连：原命令复用已保存提案和调用记录，恢复后不重复草稿。
4. 最终 COMMIT 已持久化但回应丢失：读取原完成结果，不重复模型调用、预算预留、动作或助手结果。
5. 模型调用预留 COMMIT 回应未知：原 4096 预留保持 unknown，旧租约不能补写结果，新尝试累计 8192；未知不能按失败释放预算。
6. 检查点注册 COMMIT 前断连。
7. 检查点注册 COMMIT 后回应丢失，并验证旧租约拒绝。
8. 检查点迁移等待 advisory lock 时终止本测试连接：保留原始 `57P01`，丢弃坏连接，下一次迁移成功。

[逐窗口证据](../evals/results/2026-10-23T16-23-28.948Z-g8j-planning-fault-evidence.json)记录真实断连/故障屏障与清理。早期业务断言 4/4 但进程退出 1，第二次还观察到 4 个未处理连接异常；原记录没有覆盖为通过，见[红绿退出记录](../evals/results/2026-10-23-g8j-planning-fault-run-status.json)。另有 [58 项隔离数据库专项回归](../evals/results/2026-10-23-g8j-isolated-regression.json)。这些窗口不扩大为澄清所有写入、任意物理灾难、真实云恢复或外部银行容灾。
